# 🧪 Demo 2: Kafka Log

In this lab, we demonstrate how Apache Kafka stores data on disk and how to inspect the **Kafka commit logs** using native CLI tools.

---

## 1. Create a Topic (Data channel)

Run the following command to create a single-partition topic dedicated to this lab:
```bash
/opt/kafka/bin/kafka-topics.sh --create --topic kafka-logs-test --partitions 1 --replication-factor 1 --bootstrap-server localhost:9092
```

---

## 📂 2. Archive structure from disc particion

To inspect the physical files, you need to find the correct data directory inside your container.

If you don't know the exact path (like me, in the first try), use this to help:
```bash
ls -d /tmp/kafka-logs/kafka-logs-test* 2>/dev/null || ls -d /var/lib/kafka/data/kafka-logs-test* 2>/dev/null || find / -type d -name "kafka-logs-test-0" 2>/dev/null
```

Once inside the partition directory (`kafka-logs-test-0`), run:
```bash
ls -la
```

### Expected Output:
```text
total 16
drwxr-xr-x  2 appuser appuser     4096 Oct 31 12:35 .
drwxr-xr-x 57 appuser appuser     4096 Oct 31 12:43 ..
-rw-r--r--  1 appuser appuser 10485760 Oct 31 12:35 00000000000000000000.index
-rw-r--r--  1 appuser appuser        0 Oct 31 12:35 00000000000000000000.log
-rw-r--r--  1 appuser appuser 10485756 Oct 31 12:35 00000000000000000000.timeindex
-rw-r--r--  1 appuser appuser        8 Oct 31 12:35 leader-epoch-checkpoint
-rw-r--r--  1 appuser appuser       43 Oct 31 12:35 partition.metadata
```

### 📑 Understanding the Core Files

* **`.log`**: It store real mensages in binary form (It's normal start with 0 Bytes, represents initial state)
* **`.index`**: He store an index that maps message offsets to their physical position within the `.log` file.
* **`.timeindex`**: Time-based index, allowing Kafka to efficiently retrieve messages starting from a specific timestamp.
* **`partition.metadata`**: Contains partition-specific metadata, such as the unique topic ID (`topic_id`) generated by the cluster.
* **`leader-epoch-checkpoint`**: It records the partition's leadership history, ensuring that Kafka knows exactly which broker was the leader at any given time, in order to prevent data loss in the event of failures..

## 🛠️ 3. Practical Verification & Results:

To validate how Apache Kafka persists data sequentially, follow these evaluation steps:

### Step 1: Ingesting Test Messages

Open another terminal and run the command to be the `Producer`:
```bash
/opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic kafka-logs-test
```

*Note: Type a few lines of text and press Enter after each one. Press `Ctrl + C` to exit when done.*

### Step 2: Use the inspecion command
Go back to your inspection terminal. Since the `.log` file is binary, use the native `kafka-dump-log.sh` tool to decode and read the segment:

```bash
/opt/kafka/bin/kafka-dump-log.sh \
  --files /tmp/kafka-logs/kafka-logs-test-0/00000000000000000000.log \
  --print-data-log
```

### Expected result:

```text
Dumping /tmp/kafka-logs/kafka-logs-test-0/00000000000000000000.log
Starting log read off size 0
baseOffset: 0 lastOffset: 0 count: 1 position: 0 CreateTime: 1793367360000 keySize: -1 valueSize: 31 payload: Minha primeira mensagem no log
baseOffset: 1 lastOffset: 1 count: 1 position: 112 CreateTime: 1793367385000 keySize: -1 valueSize: 25 payload: Aula pratica IBM Confluent
```

### 📑 Metadata analysis
* **`baseOffset`**: Enforces strict sequential message ordering inside the partition (Offset 0, Offset 1, etc.).
* **`position`**: The physical byte address of the record on the storage device, enabling highly efficient, low-latency lookups.
* **`CreateTime`**: The exact epoch millisecond timestamp when the message was produced, heavily utilized by Kafka's log retention and cleanup policies.
* **`keySize: -1`**: Indicates that no key was attached to this payload, meaning Kafka will automatically fallback to Round-Robin distribution across partitions.
* **`payload`**: The raw, deserialized textual data transmitted by the producer.
